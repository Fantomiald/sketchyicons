# Figma plugin for sketchyicons — Design

## Purpose

Publish sketchyicons as a public Figma plugin so designers can discover and insert the hand-drawn icon set directly on the canvas. This is a top-of-funnel discovery channel that feeds adoption of the existing npm packages (designers pick the icon style before devs implement it).

## Scope (v1)

Search + simple insertion only:

- Search icons by name and alias
- Grid of icon previews
- Click an icon to insert it onto the current page, at default style (as shipped: `stroke="currentColor"`, resolved to a solid default color, stroke-width 2)

Explicitly out of scope for v1: color/stroke-width customization controls, auto-sync tooling between the npm release process and the plugin bundle. Both are candidates for a v2 once the plugin has real usage.

## Distribution target

Public listing on Figma Community (requires Figma's review process; no fixed SLA — "reasonably prompt" per Figma's guidelines). Local/private testing happens first via "Import plugin from manifest" in Figma desktop before submission.

## Package location

New package `packages/figma-plugin` inside the existing `sketchyicons` pnpm monorepo (`lib/`), alongside `packages/react`, `packages/vue`, `packages/static`, etc. Follows the existing workspace/build-tooling conventions (`tools/build-targets.mjs` pattern, `pnpm -r --filter "./packages/**"` scripts).

## Data pipeline

Source of truth, reused as-is (no re-derivation from raw SVGs):

- `packages/static/icons.json` — flat map of icon name → path data, already generated by the existing build (`tools/build-targets.mjs --target static`)
- `packages/data/aliases.json` — old-name → current-name mapping, used so search also matches deprecated/alias names (e.g. searching "activity-square" finds "square-activity")

Build step (new, plugin-local):

1. Read `icons.json` + `aliases.json`
2. For each icon, resolve `stroke="currentColor"` to a solid default color (verified: `packages/static/icons/*.svg` ships with `stroke="currentColor"`, which does not reliably resolve inside `figma.createNodeFromSvg` — must be a concrete color before insertion)
3. Emit a single bundled JSON (name → svg string, plus alias index) embedded into the plugin build at compile time

No runtime network access — `manifest.json` sets `networkAccess: { allowedDomains: ["none"] }`. This also reduces review surface/risk since the plugin reads/writes only the local Figma document.

## Tooling

Built with `create-figma-plugin` (community-standard toolkit: TypeScript + esbuild + UI components that already match Figma's design language). Chosen over a hand-rolled manifest/esbuild/CSS setup because Figma's review guidelines explicitly require the plugin UI to "align with Figma's design language" — using prebuilt components directly reduces that review risk and the amount of UI code to write and maintain.

## Architecture

- `manifest.json` — `editorType: ["figma"]`, `networkAccess.allowedDomains: ["none"]`, points at built `main`/`ui`
- `code.ts` (plugin sandbox) — listens for an `insert-icon` message from the UI, looks up the icon's SVG string in the bundled data, calls `figma.createNodeFromSvg(svg)`, positions the new node at the current viewport center, selects it
- `ui.tsx` (iframe UI, `create-figma-plugin` components) — search input (matches name + aliases) + virtualized/paginated icon grid (1757 icons is too many to render unpaginated), each item posts `insert-icon` with the icon name on click

## Testing

No automated visual testing possible — Figma plugins run inside Figma's own sandbox, not headless. Verification loop: Claude Code builds and hands off build output, the user loads it in Figma desktop via "Import plugin from manifest", tests, and reports back (ideally with screenshots) for each iteration.

## Publishing

Claude Code prepares: manifest, code, build, listing description/usage docs, and a review-readiness checklist derived from Figma's published guidelines (no crashes, documented usage, UI matches Figma's design language, no ads, clear support contact).

Requires the user to, outside of this session:

1. Have a Figma account
2. Create the plugin entry in Figma desktop (Menu → Plugins → Development → New Plugin) to obtain the unique `id` required in `manifest.json`
3. Import and manually test the plugin locally, relaying results back
4. Supply/approve final visual listing assets (plugin icon, cover image)
5. Submit for Figma Community review and relay any reviewer feedback

## Risks / open questions

- `currentColor` resolution inside `figma.createNodeFromSvg` needs to be verified empirically during first local test — the design assumes it must be pre-resolved to a solid color, but this should be confirmed against actual Figma behavior rather than assumed indefinitely.
- Review turnaround time is unpredictable and outside our control.
